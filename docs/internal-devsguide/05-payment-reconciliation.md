# Payment Reconciliation Engine

> **Module type:** Core billing subsystem  
> **Repos affected:** EduTrack (school fees + subscription)  
> **Mirror of:** EstateTrack `docs/internal-devsguide/05-payment-reconciliation.md` — EduTrack-specific differences noted below.

---

## Overview

Same two-independent-witness model as EstateTrack. See EstateTrack doc for full concept reference. This document covers EduTrack-specific details.

### EduTrack Obligation Types

| Type | Payer | Payee |
|---|---|---|
| `fee_term` | Parent (user ID = `payer_account_id`) | School (`school_id` = `payee_account_id`) |
| `edutrack_subscription` | School (`school_id`) | Platform (sentinel UUID) |

---

## EduTrack-Specific Role Mapping

| Role | Payer for | Payee for | DB identity |
|---|---|---|---|
| Parent | `fee_term` | — | `auth.uid()` = `payer_account_id` |
| Bursar | — | `fee_term` | Submits blind payee submissions |
| School | `edutrack_subscription` | `fee_term` | `school_id` |
| Platform | — | `edutrack_subscription` | Sentinel UUID in `billing_config` |

> A bursar is simultaneously a **payee** (for fee receipts) and can be a **payer** on the school's subscription obligation. These flows are visually separated in the UI.

---

## Obligation Generation

### `fee_term` obligations
Created from existing `invoices` records via the seed section of `20260801000000_reconciliation_engine.sql`. New term invoices generate obligations automatically when created by the bursar.

### `edutrack_subscription` obligations  
Generated by pg_cron on the 1st of each month at 03:00 UTC, **only when an academic term is active** for that school. This makes billing termly (≈3x/year) rather than monthly.

---

## Blindness Rule

Identical to EstateTrack:
1. DB `CHECK` constraint on `submissions.obligation_id`
2. `submitPayeeVerification()` hardcodes `obligation_id: null`
3. RLS policy blocks bursar from inserting a payee submission with an `obligation_id`

## Server Actions

Same file structure as EstateTrack under `apps/web/app/actions/payments/`. Key difference:
- `submit-payment.ts`: checks `users.school_id` for subscription payer role (not `profiles.landlord_id`)
- `notifications.ts`: EduTrack-specific copy; subscription events link to `/bursar/billing`

---

## Cash/Cheque Confirmation

Bursars confirm cash payments via `confirmCashPayment()` in `verify-payment.ts`. This creates a `manual_override` MatchRecord tied to the original payer (parent) submission.

---

## Caretaker Role

**Not applicable in EduTrack.** The `caretaker_assignments` table exists only in EstateTrack.
